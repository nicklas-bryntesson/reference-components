RangeScale

The lane a RangeField is measured against. The field draws a track and a thumb, because a native range has exactly two addressable insides; everything else on the same lane lives here as sibling elements in a grid stack. This is the only tier in the family with JavaScript, and it has it for one reason — CSS cannot read an input's value, so anything whose length depends on it has to be told.

Interaction states

The lane has no interaction states of its own. What these rows verify is that it does not swallow the field's: hover, focus and active all still reach the thumb through the stack, and the whole lane surface remains the input's hit target.

Lane model — a documented choice

How far into the lane the thumb's centre may travel is one length, --_rs-inset, and it is the whole difference between the two models. Every layer positions with the same expression, so there is only ever one copy of the maths: 

--_rs-pos: calc(var(--_rs-inset) + var(--_rs-p) * (100% - 2 * var(--_rs-inset)))

At thumb / 2 it reduces to thumb/2 + p × (100% − thumb); at 0 it reduces to p × 100%. Pick by what the consuming layout can afford, not by which looks better in isolation.

Ticks

One element per stop, each carrying its own --p — positioned by the same single expression as the fill, because custom properties resolve on the element that uses them. A repeating gradient would be cheaper in DOM but can only express even spacing, and it needs its own period arithmetic against an inset background box.

The stops are aria-hidden, and that is not a compromise: nothing in ARIA models tick marks, and step already makes the keyboard land on exactly these values — so what the eye sees and what the keyboard feels agree without any ARIA at all. The labels are numeric by definition: a scale of words is an ordered set, which is a radio group and not a range, so there is nothing to mirror into aria-valuetext.

Native reference

The browser's own range, for comparison: no fill in Chromium or WebKit, and no readout. Firefox alone fills its track via ::-moz-range-progress — which is exactly why this component does not rely on that pseudo-element. A fill that appears in one engine and not the others is a visual inconsistency, not progressive enhancement.
