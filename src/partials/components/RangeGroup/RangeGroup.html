RangeGroup

Two RangeFields on one shared RangeScale, bounding a span. Native range has no multiple — it was never implemented — so a span is two inputs, and each one keeps its own role, its own keyboard and its own entry in the form data. The <fieldset> gives the group its intrinsic name from <legend> and the disabled cascade for free.

Hard stop is the only clamping strategy, and there is no attribute for it. The other two are not styling choices: push silently moves a value the user did not touch, and swap changes a control's identity mid-interaction — focus stays on the same element while it now drives the other end — which no ARIA mechanism can announce.

The group has no interaction states of its own. What these verify is that it does not swallow the fields': both thumbs stay reachable through the stack, and the lane keeps the pointer only where a thumb is.

When the two ends meet

On the same value the thumbs overlap and only one can be reached by pointer, so whichever is nearer the press is raised. Press near the left of the handle, then near the right — a different end moves each time. The keyboard never has this problem: Tab reaches both regardless, which is also why the swap strategy was rejected rather than styled around.

Native reference

Two plain <input type="number"> bounding the same span: zero JavaScript, no overlap, no clamping strategy, no aria-valuetext — and the value can be typed. When the span must be exact, or is mostly filled in by keyboard, this is the better answer, and it is worth asking why a slider was wanted before building the three behaviours above.
